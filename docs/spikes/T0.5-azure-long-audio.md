# T0.5 decision note: scoring long reads with Azure

| Item     | Value                                                           |
| -------- | --------------------------------------------------------------- |
| Date     | 3 November 2026                                                 |
| Author   | Gabriela Souza                                                  |
| Status   | Decided                                                         |
| Based on | TRD §6.2, BRD risk R8, task T0.5                                |
| Decision | **Chunk at sentence boundaries (REST)**. WebSocket not adopted. |

## Question

Azure's REST pronunciation assessment accepts at most 30 seconds of audio. Full-story reads and slow readers
reach 100 seconds or more. How do we score them from a Worker within 15 seconds?

## What we tested

Code: `app/lib/azure*.ts`, `app/lib/wav.ts`, `app/lib/align.ts`, and the staging-only route
`POST /api/debug/azure-spike`. The fixtures are Azure neural-voice readings of the four stories (16 kHz mono
WAV, 19 to 97 seconds), with slowed speech and long pauses to imitate a struggling reader. Every case ran
twice on staging (Cloudflare edge) and once locally. Scores were identical across runs.

- **Whole:** one REST call with the full reference text.
- **Chunked:** Deepgram word timings, then the read is split in the pauses between sentences into chunks of
  25 seconds or less. Azure scores each chunk in parallel against its own sentences, and the scores are averaged
  by reference word count.
- **WebSocket:** Azure continuous mode, using the Speech SDK's WebSocket protocol, opened from the Worker with
  `fetch` + `Upgrade`.

## Results (staging, server time)

| Recording | Whole                 | Chunked                         | WebSocket   |
| --------- | --------------------- | ------------------------------- | ----------- |
| 19–21 s   | 5.2–5.7 s             | 1.7–2.2 s (forced 8 s chunks)   | 4.0–4.4 s   |
| 33 s      | 8.4–9.4 s, C = 89     | 7.0–7.5 s                       | 6.6–7.0 s   |
| 69 s      | --                    | 6.0–6.4 s                       | 14.3–14.9 s |
| **97 s**  | 9.6–9.8 s, **C = 32** | **7.0 s** (7.4 s at the client) | 19.8–20.2 s |

Deepgram took 0.1 to 0.9 seconds of the chunked time. Chunked latency is set by the longest chunk (about 7 s
for 25 s of audio), not by the length of the read.

**Whole vs chunked, same short recording** (realistic two-chunk split, 15-second maximum):

| Recording    | Accuracy  | Fluency   | Completeness | Pronunciation |
| ------------ | --------- | --------- | ------------ | ------------- |
| Test 1, 20 s | 94 → 94.4 | 85 → 88.1 | 98 → 98.3    | 90.4 → 91.8   |
| Test 3, 19 s | 93 → 93.0 | 88 → 91.6 | 98 → 98.0    | 91.6 → 92.7   |

All within the 5-point limit. With forced 8-second chunks, fluency rose by up to 10.6 points.

## Findings

1. **Over 30 seconds, Azure fails silently.** It returns 200 and scores only about the first 30 seconds:
   completeness 32 and accuracy 31 for a full 97-second read. `assessPronunciation()` now refuses audio over
   30 seconds, so this can never reach a participant's result.
2. **Chunking meets the target with room to spare:** 7 seconds for 100 seconds of audio, against a 15-second limit.
3. **Splitting raises fluency.** A pause at a cut is not seen by Azure, so smaller chunks score higher fluency
   (+3 to +4 points with two chunks; up to +10 with many small ones). Continuous mode shows the same effect,
   because Azure splits it into phrases itself (fluency 94 to 100). Keep chunks as large as possible (25 s), and
   calibrate fluency thresholds on this pipeline (T6.7).
4. **WebSocket works from a Worker.** It connects in under 0.5 seconds, but it runs at only about 5× real time:
   20 seconds for a 100-second read, so it misses the target. It also has no miscue support (`EnableMiscue`), so
   completeness must be computed by us, and it relies on an undocumented SDK protocol (the
   `phraseDetection.enrichment` context format), which could change without notice.

## Decision

Use **chunked REST** for reads over 25 seconds. A read of 25 seconds or less is one REST call, which runs in
parallel with Deepgram. A longer read waits for Deepgram's word timings (under 1 second), then scores its
chunks in parallel. T3.3 builds on `planChunks()` and `combineChunkResults()`.

## Cost per audio minute

Taking prices from TRD §11 (recheck before launch):

- Azure costs about $1.32 an hour, or **$0.022 a minute**.
- Deepgram costs **$0.0043 a minute**. This call is already needed for the Deepgram score.
- That is about **$0.026 per minute** in total.

Chunking adds no Azure audio. It drops the silence between chunks, so it is slightly cheaper than one call.
The WebSocket route costs the same.

## Limits of this spike

The fixtures are synthetic voices with clean audio. T3.3 must repeat the whole-vs-chunked check with real
learner recordings: accents, hesitations, background noise and words cut off at boundaries. Azure's tier and
concurrency limits held for 6 parallel chunks. Recheck this under load in T6.3.
